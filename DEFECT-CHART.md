# DiamondBank-OG defect chart

| Severity | Meaning |
|---|---|
| 🔴 | Critical. Freezes the economy or server, or loses, duplicates or misdirects value or items, and any player can trigger it in normal play (API consumers included) |
| 🟠 | Serious. Wrong money or state that needs an admin action, another plugin, a reload or a rare state to arm, or a feature any player hits that is broken or refuses valid input |
| 🟡 | Minor. Bounded slowdown, wrong message or audit value, API declaration mismatch, edge-input refusal |

## 1. Public API, offline-player compatibility

| Entry point | Severity | Note |
|---|---|---|
| `K.consumeFromPlayer`, `J.consumeFromPlayer`, `K.playerPayPlayer`, `J.playerPayPlayer` (offline payer) | 🟠 item loss on stale data | **Offline calls parse the stored inventory without the DataFixer and write it back, so items an upgrade renamed become air.** `InventorySnapshot.from` uses `UtilitiesOG.getInventoryData` (`InventorySnapshot.kt:48`), which reads raw NBT from RocksDB (`PlayerDataUtils.java:36-54`, `PlayerDataStorage.java:283-293`) and parses each slot with `ItemStack.of`; a renamed id (`grass_path`, `sign`, pre-1.13 id plus `Damage`) parses as `AIR`. `restoreTo` then writes all 41 slots back even when nothing changed (`InventorySnapshot.kt:79`; called unconditionally at K:188, :255, J:249, :313), so that item is gone at next login, and when the stored `DataVersion` is below 1458 (pre-1.13) the login fixer re-wraps `display.Name` on every named item the restore wrote (`V1458.java:57-60`), including the change shards the transaction itself added, which then no longer match `removeItem` (see `removeAllShards`). Needs a target whose stored data predates such an upgrade. *Fix: have `UtilitiesOG.getInventoryData` run `MCDataConverter.convertTag(MCTypeRegistry.PLAYER, ...)` and have `setInventoryData` write the whole converted compound with the current `DataVersion` (`PlayerDataUtils.java:76-82`); skip `restoreTo` when the snapshot was not modified.* |
